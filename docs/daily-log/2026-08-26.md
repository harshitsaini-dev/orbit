# 2026-08-26

## The delete that hung at zero

Deleting 167 files sat on *"Deleting 0 of 167…"* and never moved. The batching added earlier was
not the problem — 167 was under the old cap too, so this had been broken before that change and
the cap fix had simply not touched it.

Every adapter deleted in a `for` loop: one round trip per file, one after another. From Render in
Singapore to Drive that is roughly a third of a second each, so 167 files is about a minute — and
`api.orbit.harshitsaini.in` is proxied through Cloudflare, **which closes a request after a
hundred seconds**. So it did not fail slowly, it hung: the browser waited on a request that had
already been cut, and nothing was reported either way.

Confirmed rather than guessed — `curl -D -` on the health route shows `Server: cloudflare` and a
`CF-RAY` header in front of `x-render-origin-server`.

**`bulkMap` in `packages/adapters/src/bulk.ts`**, used by all eight adapters. Six at a time, which
turns a minute into seconds. Concurrency is also the risk — too much of it is the fastest way to
be rate-limited on exactly the selection sizes where that hurts — so the limit is deliberately
modest, and yesterday's 403 handling backs off when a provider says to slow down.

A shared cursor rather than fixed slices, because a folder is a subtree and a file is one call.
Equal chunks would leave five workers idle behind whichever one drew the heavy end; there is a
test for that specific case.

Batches dropped from 100 to 50. Fifty at six at a time is a few seconds, which leaves real
headroom under the hundred-second ceiling even when a rate limit is being waited out.

## Progress where the count was chosen

The counter lived inside the confirm dialog, which is the wrong place twice over: it covers the
list it is emptying, and it keeps a modal up for the minutes a large delete takes.

The dialog now closes the moment the work starts — its warning has been read and agreed to — and
a bar appears directly above the select-all row, which is where the number being counted down was
chosen. `aria-live="polite"`: worth announcing, not worth interrupting with on every batch.

**Tests: 984 passing** (9 new on `bulkMap`, including that concurrency is bounded, that one
failure never abandons the rest, and the idle-worker case), plus 21 Playwright specs headed.

## "Could not reach Orbit" said nothing useful

Reported while deleting, and the timing matched the deploy that had just landed — Render restarts
the instance, so the API is briefly unreachable and `fetch` rejects outright. Checked rather than
assumed: `/health/ready` answers 200 in under 300ms, so nothing was actually wrong by then.

The message was still poor in both directions. A dropped connection said "Could not reach Orbit",
which reads as *broken* rather than *restarting, wait a moment*. And a gateway failure — 502, 503,
504, 524 — has no JSON body to pull a message from, since it comes from the proxy as HTML, so
`error` was undefined and the message fell through to "Request failed".

Both now say what happened and what to do. The 504/524 case matters most: it means the request
was cut for taking too long, so for anything working through a list **some of it may already have
happened**. Telling the reader to refresh before retrying is the difference between a safe retry
and assuming nothing occurred.

## The mirror is not a file tree

Reported as two things — files reappearing in My Drive after being deleted, and Refresh making it
look right again. Both were the same cause, and the cause was mine.

Reading the mirror for browsing assumed it described the same tree the provider does. One query
against production settled it: **4,860 of 5,214 rows sat at the root, and the whole database held
twelve folders.**

Two reasons, both there from the start:

- Every adapter's flat enumeration **filters folders out** — Drive by mime type, Dropbox and
  OneDrive by flag. It was written to feed the storage breakdown and the duplicate finder, which
  ask what you have, not where it is.
- Drive's `listAllFiles` **and** its delta both filed every file as `/${name}`. So each sync pass
  rewrote the row of anything that had changed, moving it to the root — which is exactly "it keeps
  coming back", once every fifteen minutes.

Refresh sends `fresh=1` and goes to the provider, so it looked correct. That is what made a data
problem present as a display glitch, and it is the part that cost the most time.

**`MIRROR_ANSWERS_LISTINGS = false`.** Listings and searches go to the provider again — the
behaviour of three days ago, slower and right. The read path and its sixteen tests are left in
place, because what is wrong is what the mirror *contains*, not how it is queried; switching it
back on is one constant once the enumeration carries folders and real paths.

The delta fix stands regardless: it now resolves ancestors through `resolveVirtualPath` instead of
assuming the root, with the cache shared across the page so five hundred changes cost a handful of
folder lookups.

**What I should have done differently.** The performance reasoning was fine and the SQL was fine.
The failure was treating "the mirror has the files" as "the mirror has the folder structure"
without checking, when a single `SELECT` would have shown it in seconds — and then writing a route
test that only asserted *which side answered*, never that the answer was right. The assertion that
would have caught this is "browsing a mirrored folder returns its subfolders", and it does not
exist. It is now written down as a precondition for turning this back on.
