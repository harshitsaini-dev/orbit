# 2026-08-26

## The delete that hung at zero

Deleting 167 files sat on *"Deleting 0 of 167…"* and never moved. The batching added earlier was
not the problem — 167 was under the old cap too, so this had been broken before that change and
the cap fix had simply not touched it.

Every adapter deleted in a `for` loop: one round trip per file, one after another. From Render in
Singapore to Drive that is roughly a third of a second each, so 167 files is about a minute — and
`api.orbit.harshitsaini.in` is proxied through Cloudflare, **which closes a request after a
hundred seconds**. So it did not fail slowly, it hung: the browser waited on a request that had
already been cut, and nothing was reported either way.

Confirmed rather than guessed — `curl -D -` on the health route shows `Server: cloudflare` and a
`CF-RAY` header in front of `x-render-origin-server`.

**`bulkMap` in `packages/adapters/src/bulk.ts`**, used by all eight adapters. Six at a time, which
turns a minute into seconds. Concurrency is also the risk — too much of it is the fastest way to
be rate-limited on exactly the selection sizes where that hurts — so the limit is deliberately
modest, and yesterday's 403 handling backs off when a provider says to slow down.

A shared cursor rather than fixed slices, because a folder is a subtree and a file is one call.
Equal chunks would leave five workers idle behind whichever one drew the heavy end; there is a
test for that specific case.

Batches dropped from 100 to 50. Fifty at six at a time is a few seconds, which leaves real
headroom under the hundred-second ceiling even when a rate limit is being waited out.

## Progress where the count was chosen

The counter lived inside the confirm dialog, which is the wrong place twice over: it covers the
list it is emptying, and it keeps a modal up for the minutes a large delete takes.

The dialog now closes the moment the work starts — its warning has been read and agreed to — and
a bar appears directly above the select-all row, which is where the number being counted down was
chosen. `aria-live="polite"`: worth announcing, not worth interrupting with on every batch.

**Tests: 984 passing** (9 new on `bulkMap`, including that concurrency is bounded, that one
failure never abandons the rest, and the idle-worker case), plus 21 Playwright specs headed.

## "Could not reach Orbit" said nothing useful

Reported while deleting, and the timing matched the deploy that had just landed — Render restarts
the instance, so the API is briefly unreachable and `fetch` rejects outright. Checked rather than
assumed: `/health/ready` answers 200 in under 300ms, so nothing was actually wrong by then.

The message was still poor in both directions. A dropped connection said "Could not reach Orbit",
which reads as *broken* rather than *restarting, wait a moment*. And a gateway failure — 502, 503,
504, 524 — has no JSON body to pull a message from, since it comes from the proxy as HTML, so
`error` was undefined and the message fell through to "Request failed".

Both now say what happened and what to do. The 504/524 case matters most: it means the request
was cut for taking too long, so for anything working through a list **some of it may already have
happened**. Telling the reader to refresh before retrying is the difference between a safe retry
and assuming nothing occurred.

## The mirror is not a file tree

Reported as two things — files reappearing in My Drive after being deleted, and Refresh making it
look right again. Both were the same cause, and the cause was mine.

Reading the mirror for browsing assumed it described the same tree the provider does. One query
against production settled it: **4,860 of 5,214 rows sat at the root, and the whole database held
twelve folders.**

Two reasons, both there from the start:

- Every adapter's flat enumeration **filters folders out** — Drive by mime type, Dropbox and
  OneDrive by flag. It was written to feed the storage breakdown and the duplicate finder, which
  ask what you have, not where it is.
- Drive's `listAllFiles` **and** its delta both filed every file as `/${name}`. So each sync pass
  rewrote the row of anything that had changed, moving it to the root — which is exactly "it keeps
  coming back", once every fifteen minutes.

Refresh sends `fresh=1` and goes to the provider, so it looked correct. That is what made a data
problem present as a display glitch, and it is the part that cost the most time.

**`MIRROR_ANSWERS_LISTINGS = false`.** Listings and searches go to the provider again — the
behaviour of three days ago, slower and right. The read path and its sixteen tests are left in
place, because what is wrong is what the mirror *contains*, not how it is queried; switching it
back on is one constant once the enumeration carries folders and real paths.

The delta fix stands regardless: it now resolves ancestors through `resolveVirtualPath` instead of
assuming the root, with the cache shared across the page so five hundred changes cost a handful of
folder lookups.

**What I should have done differently.** The performance reasoning was fine and the SQL was fine.
The failure was treating "the mirror has the files" as "the mirror has the folder structure"
without checking, when a single `SELECT` would have shown it in seconds — and then writing a route
test that only asserted *which side answered*, never that the answer was right. The assertion that
would have caught this is "browsing a mirrored folder returns its subfolders", and it does not
exist. It is now written down as a precondition for turning this back on.

## A bulk job has to outlive the page that started it

Reported exactly: start a delete, go and look at something else, the bar disappears and the delete
stops.

It ran inside My Drive. Navigating unmounts the component, and the loop doing the batching went
with it. Every reason for this was already written down in `lib/uploads.tsx`, whose own comment
says the queue used to live inside My Drive and transfers died silently when somebody navigated
to Quota. The same mistake, made again three months later, in the same file's neighbour.

`lib/bulk.tsx` is the same shape as the upload queue: a provider above the router, a job list, and
`onFinished` so an open page refreshes itself. Delete, restore and purge all go through it, which
is why the Bin's restore and purge no longer need their own batching loop either.

`BulkIndicator` sits in the header beside the upload chip. The fill *is* the progress bar with the
text on top of it, because a header has no room for two things saying one thing. The finished
state stays until dismissed — a job that completes while the reader is on another page would
otherwise finish with nothing ever having said so, and a delete of fifty thousand files is
precisely the thing somebody wants confirmed rather than inferred.

The in-page bar above select-all stays, but now reads from the queue rather than from local
state, so leaving and coming back shows the job still running instead of nothing.

**The E2E test holds the delete open.** A stubbed delete answers instantly, so a test that just
clicked and navigated would pass with the bug still there. The route awaits a promise the test
controls, so "still visible on Quota" means something. That is the assertion that was missing,
and its absence is why this shipped: the previous tests all checked what the code did, never what
survived leaving the page.

## Twenty-one drives in a menu nobody could read

Two problems in one screenshot, and they compound.

`.context-menu` had **no height limit**. With twenty-one connected accounts the switcher ran from
the top of the viewport past the bottom of it, so the last entries could not be reached at all —
and the measuring pass that decides whether to flip a menu upwards was working with a height
taller than the screen, so it had nothing useful to do.

And every entry was a Gmail address sharing a prefix and a suffix with its neighbours, differing
by three or four characters in the middle. That is not scannable at any speed.

So: the item list is capped and scrolls, and past eight entries the menu grows a filter field.
Opt-in rather than automatic — a right-click menu has eight actions somebody knows by heart, and a
search box over those is clutter. Eight is where scanning stops working, not where a list becomes
long.

Three details that would each have been a bug on their own:

- **Only the items scroll.** A filter field that scrolled out of view would defeat itself.
- **The scroll listener had to learn the difference between scrolling the page and scrolling the
  menu.** The menu closes on scroll, deliberately, so a menu never floats beside a row that has
  moved. With a scrolling list that meant it shut itself the moment somebody reached for what was
  below the fold.
- **The label needed its own element.** `text-overflow: ellipsis` does nothing to a bare text node
  in a flex row, so a long address widened the menu instead of being clipped.

The field takes focus on open, so the whole interaction is: click, type four characters, Enter.
There is a test for exactly that, and one for the case that motivated the opt-in — three drives,
no field.

**Still open, and not guessed at:** one account in that list shows as "Google Drive" rather than
an address. That is a nickname the naming pass never resolved, which is a different question from
this one and needs looking at on its own rather than papered over here.

## A banner, built from the app's own tokens

`docs/assets/banner.svg`. The colours are read out of `tokens.css` rather than approximated —
`#12151f` page, `#1c1f2b` surface, `#6c8cff` accent, `#98a1b8` muted — and the mark is the same
geometry as `BrandMark.tsx` and the favicon, scaled up, ring passing behind the hub at the top and
in front at the bottom, clipped to the hub's own disc so the two never seam.

SVG rather than PNG: crisp at any width, diffs in git, 7.6 KB.

Three things came out of actually rendering it instead of trusting the markup.

**The chips overlapped.** Their widths were eyeballed. They are now measured in a browser, and
each takes the *widest* result across three font stacks — GitHub will not have Inter, so the
chip has to fit whatever the reader's machine resolves. The row is 779 px in an 794 px space,
checked by an assertion in the generator rather than by eye.

**The file was not valid XML.** The comments named the design tokens, and a token is spelled
`--accent`: **an XML comment may not contain two hyphens in a row.** Browsers render it happily,
strict parsers reject the whole file, and that gap is exactly how a broken banner reaches a README
unnoticed. Caught by `xml.dom.minidom`, and the trap is now written into the file for whoever
edits it next.

**No style block, no CSS variables, no animation.** GitHub sanitises all three. It was also
rendered through a plain `<img>` with a data URI — the strictest path, and the one GitHub
actually uses — rather than only as inline markup where far more is permitted.

README updated alongside it: the banner at the top, bulk actions described as the background jobs
they now are, the Bin's uncapped loading, rate limits, and a sync entry that says plainly the
mirror does not back browsing. Test counts replaced with the real ones — 987 unit and integration,
399 Playwright specs — and the verification table corrected: `npm run build --workspaces` was
listed as clean and does not pass at all, because `@orbit/adapters` has no build script.

## Checking Actions, and what it found

Two things, and both were mine.

**CI was failing and I had said lint was clean.** I had run `npm run lint 2>&1 | tail -8` and then
read `$?` — which is the exit status of `tail`, not of npm. It was always going to be zero. Five
lint errors went in, and the verification table in this repo was updated to say there were none.

The errors were all from the last two days: imports left in `sync.ts` when the mirror writer moved
out of it, a deliberate non-Error `throw` in `bulk.test.ts` that the rule is right to object to in
general and wrong about here, and a redundant type assertion in `http.test.ts`. Fixed, and this
time the exit code was read from the command that produced it.

**The E2E job had been running for over an hour.** CI runs `playwright test`, which is all three
projects, one worker, two retries. I had only ever run my new specs on desktop. `bulk-jobs` clicks
a sidebar link to navigate away, and a phone has no sidebar — so each attempt burned the full
sixty-second timeout, three times, on two projects.

That spec is now desktop-only, and the exclusion lives in `playwright.config.ts` where the project
matrix is. It covers *where a job lives*, which is not viewport behaviour; `page.goto` would not
do instead, because a full reload loses an in-memory job legitimately and would prove nothing.

Both workflows also grew a `timeout-minutes`. The default is six hours.

**And a full local sweep, which had not been run in a while: 370 pass, 25 fail, all on mobile.**
Before blaming the menu work, two of them were run against a commit from before it — they fail
there too, identically. They are specs written for the desktop sidebar. Recorded in the project
state as a known issue rather than quietly left red.

One good result out of the same investigation: the drive-picker filter *does* work on a phone.
Its first mobile run failed, which looked like a real problem; run on its own it passes 5 of 5 in
36 seconds. The failure was interference from `bulk-jobs` in the same invocation.

### And then actually fixing the mobile specs

The `timeout-minutes` cap did its job and cancelled the next E2E run at twenty-five minutes, which
made the arithmetic obvious: 25 failures × 3 attempts × a 60-second timeout is over an hour of
retries on its own. Capping stopped the bleeding and guaranteed the job could never go green.

So they got fixed rather than skipped. `goToPage()` in `e2e/helpers.ts` uses whichever navigation
the viewport has — the sidebar link on a desk, the `NavPicker` dropdown on a phone. Navigating is
a means in nearly all of those specs, not the thing under test, so this keeps the coverage on both
layouts instead of scoping the tests to desktop and pretending the phone is tested.

Two of them were different and needed reading rather than a helper:

- **`every navigation item is reachable`** still described a horizontal strip of links that
  scrolled sideways. That was replaced by the dropdown weeks ago, so the one test written *for*
  the phone was failing on the phone. Rewritten against what is actually there, and its sibling
  now measures whichever navigation exists.
- **The webhook dialog's event list sits below the fold on a phone.** `check({ force: true })`
  skips the actionability checks but Playwright still will not click outside the viewport. The
  dialog is scrolled first, which is what a person does and what its own overflow is for.

**394 of 395 pass, in four and a half minutes**, down from 370 of 395 in ten. The one failure —
`providers.spec.ts` on mobile — passes 7 of 7 when that file runs alone, so it is flaky under the
full parallel run rather than broken. Written down as such rather than re-run until it was green.
