# 2026-09-08

## Checking Actions, and what it found

Two things, and both were mine.

**CI was failing and I had said lint was clean.** I had run `npm run lint 2>&1 | tail -8` and then
read `$?` — which is the exit status of `tail`, not of npm. It was always going to be zero. Five
lint errors went in, and the verification table in this repo was updated to say there were none.

The errors were all from the last two days: imports left in `sync.ts` when the mirror writer moved
out of it, a deliberate non-Error `throw` in `bulk.test.ts` that the rule is right to object to in
general and wrong about here, and a redundant type assertion in `http.test.ts`. Fixed, and this
time the exit code was read from the command that produced it.

**The E2E job had been running for over an hour.** CI runs `playwright test`, which is all three
projects, one worker, two retries. I had only ever run my new specs on desktop. `bulk-jobs` clicks
a sidebar link to navigate away, and a phone has no sidebar — so each attempt burned the full
sixty-second timeout, three times, on two projects.

That spec is now desktop-only, and the exclusion lives in `playwright.config.ts` where the project
matrix is. It covers *where a job lives*, which is not viewport behaviour; `page.goto` would not
do instead, because a full reload loses an in-memory job legitimately and would prove nothing.

Both workflows also grew a `timeout-minutes`. The default is six hours.

**And a full local sweep, which had not been run in a while: 370 pass, 25 fail, all on mobile.**
Before blaming the menu work, two of them were run against a commit from before it — they fail
there too, identically. They are specs written for the desktop sidebar. Recorded in the project
state as a known issue rather than quietly left red.

One good result out of the same investigation: the drive-picker filter *does* work on a phone.
Its first mobile run failed, which looked like a real problem; run on its own it passes 5 of 5 in
36 seconds. The failure was interference from `bulk-jobs` in the same invocation.

### And then actually fixing the mobile specs

The `timeout-minutes` cap did its job and cancelled the next E2E run at twenty-five minutes, which
made the arithmetic obvious: 25 failures × 3 attempts × a 60-second timeout is over an hour of
retries on its own. Capping stopped the bleeding and guaranteed the job could never go green.

So they got fixed rather than skipped. `goToPage()` in `e2e/helpers.ts` uses whichever navigation
the viewport has — the sidebar link on a desk, the `NavPicker` dropdown on a phone. Navigating is
a means in nearly all of those specs, not the thing under test, so this keeps the coverage on both
layouts instead of scoping the tests to desktop and pretending the phone is tested.

Two of them were different and needed reading rather than a helper:

- **`every navigation item is reachable`** still described a horizontal strip of links that
  scrolled sideways. That was replaced by the dropdown weeks ago, so the one test written *for*
  the phone was failing on the phone. Rewritten against what is actually there, and its sibling
  now measures whichever navigation exists.
- **The webhook dialog's event list sits below the fold on a phone.** `check({ force: true })`
  skips the actionability checks but Playwright still will not click outside the viewport. The
  dialog is scrolled first, which is what a person does and what its own overflow is for.

**394 of 395 pass, in four and a half minutes**, down from 370 of 395 in ten. The one failure —
`providers.spec.ts` on mobile — passes 7 of 7 when that file runs alone, so it is flaky under the
full parallel run rather than broken. Written down as such rather than re-run until it was green.

### The test that could only fail on CI

With the specs fixed and two workers, the E2E job finished for the first time in days: **391
passed, 3 failed, 1 flaky, 22 minutes** — under its ceiling rather than cancelled by it.

All three failures were one test, `quota-filter`, on all three projects. It passed 9 of 9 locally.

The difference was `.env`. The Quota page has two lists of drives — the ones connected, and the
ones this instance has no keys for — and both are `.clay-sunken` cards. A developer machine has
Dropbox keys, so Dropbox is only in the first list and the count is one. CI has no keys, Dropbox
is in both, and the count is two. The test had been written against one machine's configuration
and could not have passed anywhere else.

Proved in both directions rather than reasoned about: with the keys unset the old code fails with
CI's exact message, and with the fix it passes.

The locator is now scoped to the connected accounts, which needed the list to be identifiable —
so it has `aria-label="Connected accounts"`. That is not a test hook. A screen reader had no way
to tell "the drives you have connected" from "the drives you could connect", and neither did the
test; naming it fixes both.

**Then the whole suite was run again with the provider keys unset**, which is the shape CI runs
in. No further deterministic failure — the four that came up were flaky, passed on retry, and were
a different four the second time. Those are now recorded as known flakes, along with the general
lesson: when CI disagrees with a local run, `.env` is the first place to look, and
`DROPBOX_CLIENT_ID= GOOGLE_CLIENT_ID= npx playwright test` reproduces it.
