  re-optimised and forced a reload that aborted whatever navigation was in

## Later that day — thumbnails everywhere, and sharing a drive

### Thumbnails on stores that make none

Drive renders previews and Orbit proxies them; object stores render none, so an
R2 or Supabase bucket full of photos was a grid of file icons. The interim fix
served the original image as its own tile, which drew a few hundred pixels using
whole megabytes.

`services/thumbnails.ts` now generates them: fetched once, resized to fit,
re-encoded WebP at quality 72, held in a 32 MB in-memory LRU. An in-flight map
means forty tiles of the same image decode once, and decoding is capped at two
concurrently because this process also serves requests somebody is waiting on.
Nothing is written to disk — a derived image is still bytes, and not storing
bytes is the rule the product is built on.

Measured against the real buckets:

| Source | Original | Thumbnail | |
| --- | --- | --- | --- |
| Supabase `avatar.jpg` | 994 KB | 4.9 KB | 200× |
| R2 PNG | 151 KB | 11 KB | 13.5× |
| R2 PNG | 95 KB | 3.8 KB | 25× |

Cold ~0.3 s, cached ~0.1 s.

The grid also stopped asking about files that cannot have a picture. A folder of
five hundred text files was spending five hundred requests to learn that none of
them had one.

**Not covered, and flagged rather than attempted:** Drive also makes thumbnails
for video, PDFs and documents. Matching that on S3/MEGA/Dropbox needs ffmpeg and
a document renderer — sustained CPU the free tier does not have, competing with
request serving on the single node. Images work everywhere; the rest shows an
icon. That is a paid-compute decision for the owner.

### Sharing a drive with other people (Phase 8, first half)

Access is granted **per drive**, not per Orbit account — ADR 0011. Four ordered
levels: `read`, `write`, `full` (delete and publish links), `admin` (bring other
people in). Somebody with no grants sees nothing.

Per drive rather than per workspace because a workspace role cannot express the
ordinary case: somebody added for the team bucket would also see the personal
Drive connected beside it.

Members sign in as themselves — own address, own code, own session. No
accept-link: a link proves only that somebody has the link, whereas a code sent
to an address tests that the address is theirs.

The change that did the most work was making `need` a **required** argument to
`useAccount`. It could have defaulted to `read`, and then any mutating caller
that forgot to pass anything would quietly have let a reader delete files. As a
required argument it produced twenty-six compiler errors, one per place that had
to decide what it was actually doing.

Two gaps that turned up while wiring it:

- Search and the smart views only ever enumerated the caller's *own* accounts, so
  a guest would have found nothing on a drive shared with them. Both now run over
  every readable drive.
- Allocation was left owner-only on purpose. Automatic upload placement choosing
  among drives you merely have write access to would put your files in somebody
  else's storage without you asking.

`app.test.ts` was running against the developer's own `orbit.db` rather than a
throwaway one, so migration 0010 failed there instead of where it belonged. It
now uses `useTestDatabase` like every other route test.

## Later still — Dropbox verified, ESLint, and Phase 19

### Dropbox, end to end

Credentials went into `.env` and the account connected. Verified against the real
account rather than assumed: upload (11.5 KB JPEG), listing, thumbnail (Dropbox
renders its own, 3.4 KB), download byte-for-byte identical to what went up, a
Range request returning 206, search finding it, and delete leaving the folder
empty.

One thing the round trip exposed: files came back as `image/*`. That is a match
pattern, not a media type — meaningless in a `<video>` source, wrong as a
`Content-Type`, and false to anything comparing against a specific type rather
than a prefix. Both Dropbox and OneDrive describe a file only as "image" or
"video", so `mimeForName` now maps the extension to a real type, falling back to
`application/octet-stream` rather than to a wildcard.

### ESLint

`npm run lint` has been failing to run at all since ESLint 9 stopped reading
`.eslintrc` — there was no config file. CI never ran it, which is why it went
unnoticed.

The config is aimed at what `tsc` compiles happily: un-awaited promises, empty
catches, drifted hook dependencies. Everything switched off is switched off with
its reason written next to it.

It found three real bugs:

- `ws.ts` stringified frames with `raw.toString()`. The `ws` library hands over a
  Buffer, an ArrayBuffer, or an array of Buffers depending on how the frame
  arrived; the last two give `"[object ArrayBuffer]"` and a parse failure that
  nothing would have explained.
- `ShareDialog` and `TransferDialog` wrapped `Checkbox` in a `<label>` — but
  `Checkbox` renders its own `<label htmlFor>`. Nested labels are invalid HTML
  and a click can toggle twice.
- An e2e assertion built a RegExp from `path.replace('/', '\/')`, which in a
  plain string is just `'/'` — a no-op standing in for an escape never needed.

It also caught two imports left dangling by the mime change earlier the same day,
which is the argument for having it run in CI. It does now, between typecheck and
the tests. 0 errors; 28 warnings, all React Compiler notes about setting state in
an effect, most of which are the documented way to reset state when a prop
changes.

### Phase 19 — scheduled jobs

Routes and UI on top of the service written earlier. They tick on the existing
node-cron pass, in a function of their own so a broken schedule cannot stop token
refresh.

Two decisions worth recording:

- Drives are checked **at the level the job will need** when the schedule is
  created — a backup target for `write`, not merely for existing. Finding out at
  2am that a job was never going to work costs a week of believing it was
  running.
- "Run now" does not move `nextRunAt`. Pressing it at four in the afternoon must
  not turn a nightly job into a four-in-the-afternoon job.

The page states plainly that jobs run late rather than not at all, because the
instance sleeps. Better said outright than discovered.

Verified live against the real Drive: created, ran on demand (`ok`, "0 changed,
0 removed", `nextRunAt` unmoved), paused, deleted.

## Video and PDF thumbnails, on when the machine can afford them

Earlier today the answer to "thumbnails for video and PDFs too" was: not on a
free tier. That is still true of the free tier, but it was the wrong shape for
the answer — it left a capability unwritten rather than unavailable.

`services/renderers.ts` now looks for `ffmpeg` and `pdftoppm` once at start-up.
The feature exists exactly when the tool does. Nothing found: those files show an
icon and not a byte of a video is ever fetched, because the availability check
happens before the fetch rather than after it. ffmpeg present: video thumbnails
start appearing, with no flag to set and no code path that was written and then
never used. The boot log says which it found, so nobody has to infer it.

`ORBIT_FFMPEG` and `ORBIT_PDFTOPPM` name the binaries when they are not on PATH.

Two deliberate limits:

- A video is read as a 12 MB **prefix**, not in full. That prefix has to contain
  the index — MP4s written with `faststart` decode, ones that put it at the end
  return null. Better than pulling two gigabytes through the server to be sure.
- Nothing touches disk. The bytes go in on the renderer's stdin. A temp file
  would be simpler and would let ffmpeg seek freely, but it would also mean
  writing a user's file to Orbit's disk, which is the one thing this product
  does not do.

### A real Windows bug found while testing this

Since CVE-2024-27980, Node **refuses to spawn a `.cmd` or `.bat` on Windows**
without a shell — it throws EINVAL rather than returning an error. That is not a
corner case: scoop installs ffmpeg as a `.cmd` shim, so a Windows machine that
plainly had ffmpeg would have reported that it did not.

Those two extensions now go through `cmd.exe` with the arguments quoted by hand,
including the outer pair `/s` requires — without it the path and the first
argument arrive fused into one token. Nothing user-supplied reaches the argument
list: every argument is a literal in that file and the file itself goes in on
stdin.

The tests exercise the real spawn-and-pipe path against shims rather than
mocking it, which is how the EINVAL surfaced at all.

### Verified

- 644 unit tests green, 0 lint errors.
- This machine has neither tool, and reports so: `thumbnails: images only
  (install ffmpeg for video, poppler-utils for pdf)`.

## Moving and copying, inside a drive and across two

Four ways to put a file somewhere else, split along the two axes that actually
differ: whether the original survives, and whether the bytes have to travel.

**Inside one drive** is new. `relocate` on the adapter contract, gated by a
capability of the same name, implemented for Drive, Dropbox, OneDrive and every
S3-compatible store. The provider does the work; nothing is downloaded and
re-uploaded. Each was a different shape:

- **Drive** — a move is a change of parent, and both the old and the new one have
  to be named, because a Drive file can legitimately sit in several folders at
  once. Copy is `files/{id}/copy`.
- **S3** — no folders and no move, only CopyObject. A move is a copy then a
  delete, all copies before any delete: the other order leaves a half-moved
  folder with the original already gone if one fails.
- **Dropbox** — paths *are* the ids, so this is the same RPC as renaming with a
  different destination. `autorename: false`, because a silent "a (1).jpg" is
  worse than an error somebody can act on.
- **OneDrive** — move is a `parentReference` patch; copy is not, Graph makes it
  an async job answering 202 with a URL to poll.

**Across two drives** was already the transfer engine, but it was one menu item
and a checkbox. It is now two items, "Copy to another cloud" and "Move to
another cloud", with the checkbox still there to change your mind. A checkbox
that decides whether the original is deleted is not a thing to bury in a dialog
somebody is skimming.

The destination is browsed, not typed — people know a folder by recognising it,
and a typed path is a spelling test with a 404 for a wrong answer. The picker has
a fixed height on purpose: a dialog that grows as you browse moves its own
buttons out from under the cursor.

A move needs `delete` on the drive, not `write`. It takes the file away from
where it was, which is the thing `write` deliberately does not permit.

- Live against the R2 bucket: copied a file into a new folder (original still
  there), moved it back (source folder empty, so a move and not a copy), 400
  with no destination, 404 for an account that is not the caller's, cleaned up.

## Consistency, and the drift it exposed

A long stretch of the day was one complaint repeated: a feature built on My
Drive had not reached the other pages that show files. That was fair, and the
fix was structural rather than a list of edits — the view switch, the filter and
the sort live in one component now, so Recent, Starred, Shared with me,
Collections and Uploads got all three at once and the next thing added lands
everywhere by default.

Chasing that turned up four pieces of drift worth recording, all of the same
kind: a second copy of something that had quietly stopped agreeing with the
first.

- The upload-allocation route validated the strategy against a **hand-copied
  enum** that had never been updated. It silently rejected a strategy the rest
  of the app already offered. It derives from `ALLOCATION_STRATEGIES` now.
- The connect route asked for the account's identity only when the adapter was
  Google Drive. Dropbox and OneDrive both implement it and were never asked, so
  every Dropbox connection was called "Dropbox" and had no remote id — which
  also meant reconnecting one added a second row instead of updating the first.
- Every `var(--bg)` in the stylesheet referred to a token that does not exist.
  Four rules had been painting nothing.
- `listAllFiles` asked Drive for every drive the account could see. That feed is
  what the breakdown, the duplicate finder and search all read, so a 15 GB Drive
  was reporting a breakdown of storage it does not own and cannot free.

The last one is the important one. A shared drive belongs to an organisation:
Google bills it to them, reports it under a quota of its own, and does not count
it against anybody's allowance. Orbit was counting it. It now asks for the
account's own corpus, and shared drives have a page of their own rather than a
folder inside somebody's My Drive — which had got three separate things wrong at
once: who owns it, who else can see it, and whose storage it fills.

Verified against the Workspace drive actually shared with this account. It lists
under Shared drives and opens; clicking into it used to 404, because the
synthetic folder's id was reaching Drive as a query parent and the throw skipped
the fallback that knew what to do with it.

### Also

- **Details panel**, from the context menu. The rows worth having are the last
  two: size and kind are in the listing already, but where a file lives and
  whether anyone outside can reach it are not visible anywhere.
- **Dashboard** split by whether storage has an allowance or a bill, with a
  file-kind breakdown for each half and for everything. The split is on
  `reportsQuota`, so a new adapter lands on the right side without this being
  touched.
- **Status screens** are portalled to the body. Returned from a page component
  they sit inside the shell, so filling the viewport still left the navigation
  drawn around them. The E2E check for it was wrong too — `toBeInViewport`
  reports a covered element as still in the viewport.
- **"Ask me every time"** declines to pick rather than being an option that
  reads well and does nothing, and the route answers it distinctly from "no
  room": a question to put and a problem to report must not look the same.

### Not done, and why

Dropbox team spaces and OneDrive's SharePoint libraries were asked for as the
equivalent of shared drives. They are not equivalent: Dropbox mounts shared
folders inside the ordinary tree rather than as separate roots, and OneDrive is
not connected to this instance at all. Writing either without an account to run
it against would be shipping untested code that looks finished, so it is flagged
rather than attempted.

- 659 unit tests green, 0 lint errors, build clean.
- Headed E2E: status screens, workspace views, schedules, sharing, file actions.

## Pagination, and measuring a thing properly

Two limits, both of which had been quietly wrong rather than loudly broken.

### The views truncated instead of paging

Recent, Starred and Shared with me fetched a page from every account, merged
them, sorted, and **threw away everything past the hundredth** — with nothing to
say the view was incomplete. Somebody with more than a hundred simply never saw
the rest and had no reason to think anything was missing.

They page now, on the per-account cursor search already used. A merged view has
no single position to remember, so the cursor is every account's position at
once. Sorted within the page and re-sorted by the client over everything
accumulated, because a later page can hold something older than the page before
it — that is what merging streams means.

Verified: 143 + 100 + 58 files across three pages, where it used to stop at 100.

The cursor helpers moved into a shared module. Search had them and the views did
not, which is exactly how the views ended up truncating — and a second copy is
how the two would have drifted apart again. That is the fifth piece of drift of
this kind today.

### Measuring a shared drive belonged in the background

Doing it on a request gave a capped, wrong answer that had to be labelled "at
least". Moving it to the sync pass — where nobody is waiting — removes the
reason for the cap entirely.

The difference on the real drive is the argument for it:

| | On request, capped | In the background |
| --- | --- | --- |
| Size | "at least 2.12 GB" | **7.65 GB** |
| Files | "25,000+" | **50,718** |
| Complete | no | yes |

The honest answer was 3.6× larger than the one a request could afford to give.

Figures are written to `shared_drive_stats` rather than held in memory: they
have to survive the restart between the pass measuring one and somebody looking
at it. The page opens on the last figure and says when it was taken, and the
button is for impatience rather than for the ordinary case.

**Removing the cap turned up a real bug.** Without one, a provider that keeps
returning a cursor loops for ever — and this runs unattended, so nothing would
notice. There is a bound again, but set far above any real drive (a million
files) as a runaway guard rather than as a page size, and hitting it marks the
result partial.

## pCloud, and the share page grows a real viewer

### Built

- The pCloud adapter, which finishes Phase 3. Items are addressed by numeric id
  rather than by path: ids survive a rename, and the trash only speaks ids, so a
  bin keyed on paths could not restore anything whose folder had since moved.
  Two things needed care - the account lives in either the US or the EU region
  and only the token response says which, so the host is stored with the token;
  and pCloud answers HTTP 200 with a `result` code, so a failure looks like a
  success to anything checking only the status. Its bin is real and an ordinary
  account may empty it, so Bin gets restore and permanent delete for pCloud too.
- The share page now mounts the workspace's own viewer (ADR 0012). A shared
  spreadsheet, archive, font or document opens the way its owner sees it instead
  of offering a download; the server still renders a page that works without any
  of it, and the bundle replaces that page rather than being required by it.

### Changed

- The scaffold test had no example left once pCloud landed. It asserts the rule
  instead: every entry in the catalogue has a real adapter behind it.
- Bin's countdown knows pCloud's retention. It is fifteen days on the free plan
  and thirty on a paid one and Orbit cannot see which, so the shorter is used -
  a file that outlives its countdown is a pleasant surprise, one destroyed
  before it is not.
- Provider cards on Connect an account fill their row rather than sizing to
  their blurb. One provider needs two lines to describe and the next needs one,
  and three different heights read as a broken layout.
- An empty `scope=` is no longer sent on an authorise URL. pCloud has no scopes,
  and asking for none is not the same as not asking.

## EXIF, the bytes, and models — Phase 16 finished

### Built

- An EXIF reader, written here rather than pulled in. It needs the *beginning*
  of a file rather than the file: EXIF sits in the first marker segment of a
  JPEG, so a range request for the first 256 KB is enough however large the
  photo is. JPEG, PNG's eXIf chunk and bare TIFF all end at the same TIFF
  header, so there is one reader behind all three, and both byte orders are
  handled because half the camera makers write big-endian.
- Camera, lens, exposure, ISO, focal length, dimensions and location now show
  on a photo's Details panel. GPS is its own row with a caution: it is the one
  field that is about a person rather than a file. A link to a map rather than
  an embedded one, so the coordinates only reach a mapping service if somebody
  chooses to go there.
- A hex view for files nothing can render, reached from "Show bytes" on the no
  preview screen. Four kilobytes at a time over a Range request, with the file
  signature named above it — the point is answering "what actually is this?"
  for a file whose name and type disagree.
- A 3D viewer for `.glb`, `.gltf`, `.obj`, `.stl` and `.ply`. three was already
  a dependency for the landing hero, so this costs a loader, and the loaders
  are imported on demand. The camera frames the model from its own bounding
  box: models are authored in millimetres or in metres, and a fixed camera puts
  half of them inside the near plane and the rest at a dot.

### Verified

- The EXIF reader against a real photo out of the connected Drive, over the
  live content route: vivo Y75 5G, 1/100s, f/1.8, ISO 542, 2296 × 4080. The
  range request came back 206 with exactly the 256 KB asked for.
- The model and hex viewers in a real browser, through a share link — which
  also proves the share page picks up viewers added after it was built.

### Fixed

- One E2E check compared a fixed, inset-0 element against `innerWidth`
  exactly. Under mobile emulation the device pixel ratio puts it at 393.6
  against 394, so a screen that visibly filled the viewport failed the
  assertion. A pixel of slack: what is being asserted is that nothing shows
  around it, not arithmetic.

## Hardening, before there is anything to harden

### Built

- One logger every line of server output goes through. Two reasons rather than
  one: redaction, because Orbit holds OAuth tokens, session cookies and one-time
  codes and a log is the easiest place for one to escape - not through a
  deliberate `console.log(token)` but through logging an object that happens to
  contain one, or a URL with `?access_token=` in it. And shape: production wants
  one JSON object per line, a person watching a terminal does not, and both come
  out of the same call.
- A request id on every response, echoed in the error a user sees. "It said
  something went wrong" is unanswerable without one. An id supplied by a caller
  is only kept if it is short and plain - it is a header a stranger can set, and
  it ends up on every line about the request.
- `/health/ready`, which asks the database a question and answers 503 if it
  cannot. `/health` answers from memory and would keep saying "ok" with the
  database unreachable, which is exactly the instance a deploy must not switch
  traffic to.
- Production configuration checks at boot (ADR 0013). The one that matters most
  is `AUTH_MODE`: local mode has no sign-in at all, and on a public host that is
  an open drive.
- Crash handlers and a real shutdown. A WebSocket by design never ends, so
  `server.close()` waited on connections built not to close - a shutdown that
  looked hung until the platform killed the process. Sockets are now told the
  server is going away, and a ten-second grace period ends in exiting on purpose
  rather than being killed.
- `render.yaml` and `vercel.json`, so the deploy is a blueprint rather than
  settings typed into two dashboards. The build command on Render includes the
  web workspace - the share page's viewer is built from it into the server, and
  `npm ci` alone would deploy an API whose share links have no viewer. The
  owner-setup document said exactly that, and now does not.
