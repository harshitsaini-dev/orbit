# 23 August 2026

## Google, published

The app is **In production**. Google accepted the homepage, `/privacy` and
`/terms` and published it without demanding verification — so the seven-day
refresh token expiry is gone, and any Google account can connect rather than
only the test-user list.

Two things carry forward: the app is published but unverified, so a new user
sees "Google hasn't verified this app" and has to choose Advanced → Continue;
and an unverified app on a restricted scope has a 100-user lifetime cap that
cannot be reset. Full verification of the `drive` scope means an annual
third-party security assessment that is not free, so it waits until Orbit is
actually being opened to a crowd.

The console's **Data access** page lists no scopes at all, which is expected —
Orbit asks for them in the authorisation request rather than registering them
on the consent screen. It is probably also why publishing went through
unchallenged, and it is the reason to leave that table empty.

**One correction worth recording.** The advice written here first was to
disconnect the drive and reconnect it, to get a token issued outside Testing.
That is wrong: disconnecting cascades, taking the drive's share links, its
collection items, its transfer history and any grants given to other people
with it. Connecting an account Orbit already has updates that row in place, so
a reconnect costs nothing. The docs say so now.

## Dropbox, nothing to do

The 50-account cap written in these docs was wrong. Development status links up
to **500** users, and Dropbox's own production request form says that an app
which does not need more than 50 should not apply, and that an application is
not reviewed until the app already has 50 users.

Branding is filled in anyway — that is what the authorise screen shows, and a
puzzle-piece icon with no publisher reads as something not to grant access to.
Icons at 64 and 256 were generated for it. Revisit at 50 accounts, when Dropbox
allows two weeks to apply.

## Privacy and terms

Written because Google needed them, kept because an app that asks for somebody's
whole Drive owes them a plain account of what it does with it. Both public,
outside the auth gate — a consent screen links to the policy for somebody who
has not signed in and may be deciding not to.

Every claim maps to something in the source: AES-256-GCM for provider tokens, a
SHA-256 hash for API tokens, no file bytes on disk at any point, no provider URL
reaching the browser, a device class and no IP for a public link, ninety days of
retention. The Limited Use paragraph is there because it is accurate, not as a
formality.

## Downloads: four asked for, one arriving — then none

Two goes at this one.

The content URL is on the API's own origin, and a link's `download` attribute is
ignored cross-origin — so every hidden anchor was a top-level navigation, and
starting the second aborted the first before the provider had answered.

Hidden frames fixed the cancellation and broke everything else: they depend on
the API's framing headers being exactly right, which is a lot of distance
between pressing Download and a file appearing.

The answer was to stop needing anything from the server. Each file is fetched
and handed over as a blob; a blob URL is same-origin, so `download` means
something again — real filenames, no navigation, nothing to cancel. One at a
time, each released as soon as it is taken, so only one file is held at once.
The API went back to refusing every frame.

## Dragging inside the grid offered to upload what was already there

Chrome puts `Files` in the transfer when an `<img>` is dragged, so nudging a
thumbnail across the grid raised the upload overlay — and letting go uploaded a
second copy of the file that thumbnail was of. A drag that began inside the page
is ignored now, and thumbnails are not draggable at all.

## A phone has no right button

Every action except delete lived behind the context menu, so on a touch screen

And the page says which drive it is showing. The switcher only appeared with two

## Duplicates, on a screen it fits on

The header pushed two of three things right with `margin-left: auto`, which
wrapped into three ragged right-aligned rows with no common edge to read down,
and left the set's two actions half off the screen.

The rows had it backwards as well. Every copy in a set has the same name — that
is what makes it a set — so the name is the one thing identifying nothing, and
the path is the only thing that tells two copies apart. The name had the room
and the path was cut, and which drive a copy was on, the whole question when the
copies are on two different clouds, was hidden outright below 700px.

A real bug fell out of it. The path was shortened with `direction: rtl` and an
ellipsis, which renders a leading slash at the right-hand end — `/a/b/photo.jpg`
was drawn as `…b/photo.jpg/`, a path that does not exist. It is shortened in
code now. Bidirectional text reordering is not a truncation tool.

## Phase 20 — reading the text in a picture, built and then removed

Built in full, both halves, and taken back out the same day at the owner's
request. What follows is what it was, so the decision is on the record and the
work is findable in history rather than guessed at.

The server stores readings and searches them. A reading under 45 confidence or
8 characters is refused rather than kept: an unreadable photo produces
confident-looking noise, and the costs are not symmetric — a missing result is a
search that fails visibly, a wrong one is a search that lies. Refusing also
clears any earlier reading, because the reading is about the file and the file
has changed. `LIKE` rather than FTS5; this holds one person's receipts, and a
virtual table with triggers to keep it in step is a cost to pay when the
difference can be felt.

The client is Tesseract compiled to WebAssembly, in a Web Worker. Nothing is
uploaded — the bytes the browser already fetched to draw the picture are the
bytes it reads, and only the resulting string comes back. That is the whole
economics of the feature: server OCR is a bill per page, and a product whose
first rule is that it stores none of your files has no business posting them to
a vision API instead.

The engine is served from Orbit's own origin. The CSP allows scripts and workers
from `'self'` only, and loading a CDN worker would tell a third party who is
scanning what — which the privacy policy says does not happen.
`scripts/vendor-tesseract.mjs` copies three LSTM core builds out of node_modules
and downloads the fast trained data at build time: 14 MB, gitignored, and
excluded from the service worker so no install of Orbit pays for a feature most
sessions never touch. A browser fetches about six megabytes of it, once.
`'wasm-unsafe-eval'` had to go into the CSP — it permits WebAssembly and nothing
else.

Scanning is asked for and never automatic. It says what it will cost before it
starts, it can be stopped in the middle, and everything read up to that point is
kept. Files already read are skipped, so scanning a folder, adding two photos
and scanning again costs two.

Results found this way carry the line they matched on, because a file called
`1759653621497799480627.jpg` appearing in the results for "sharbat" reads as a
bug until the reason is beside it.

**A bug worth remembering.** The first run finished instantly having read
nothing. The cancel flag is a ref, set to `true` in an effect cleanup — and
StrictMode mounts, unmounts and mounts again in development, so that cleanup ran
once before anybody had pressed anything. A flag only ever set to `true` meant
the loop stopped on its first check, every time, in a way that looked exactly
like OCR finding nothing at all. It is cleared on the way in now as well as set
on the way out.

The end-to-end test runs the real engine over a rendered receipt and asserts the
words that come back — `NATIONAL MARKET`, `17842`, confidence above 60. A mocked
engine would only prove that a button calls a function.

## Phase 11 — webhooks

A token lets a program ask Orbit questions; a webhook lets Orbit answer one
before it is asked. Six events, all of them facts rather than intentions: an
upload finished, a file went, a link was made, a link was opened, a transfer
ended either way, a sync changed something. An event fired before an operation
completes is one a receiver cannot act on without asking what actually happened.

**Where a webhook may point took most of the care.** A URL here is an address
chosen by a user and fetched by the server — the definition of a server-side
request forgery — and Orbit runs somewhere with a metadata service on a
link-local address that hands out the instance's own credentials to anything
that asks.

So: every private and loopback range refused, judged on the *resolved* address
rather than on how the host is spelled, and against *every* address a name
answers with rather than the first — a name resolving to one public and one
private address would otherwise pass on the strength of the public one. Plain
http is refused on a deployed instance, because a signed payload sent
unencrypted is still readable by anyone on the path. Redirects are not followed;
a redirect is an address the check never saw.

One gap is left and named in the code rather than pretended away: a name whose
DNS record changes between the check and the request. Closing it means resolving
once and connecting to the address instead of the name, which needs a custom
agent.

Deliveries are signed with `HMAC-SHA256(secret, "<timestamp>.<body>")`. The
timestamp is inside the signature, so a captured delivery cannot be replayed
next week. Retried three times, but only for what a retry could fix — a refused
connection, a timeout, a 5xx, a 429. A 400 is the receiver saying it does not
want this. Ten consecutive failures switch a webhook off rather than hammering
an address somebody else may own by now, and turning it back on clears the count.

The secret is stored in the clear, unlike an API token, and that is not an
oversight: a token is only ever compared against a hash, while a secret is
*used* to sign, so the signing side has to read it back.

Emitting never blocks and can never fail what caused it. An upload that
succeeded and then reported an error because somebody's server was down would be
Orbit lying about its own work.

The screen answers the two questions people actually have about a webhook — did
it ever fire, and what did my server say — so the delivery history is one click
from the list rather than something to infer from logs at the far end.

**Production was migrated** after the code landed: `webhooks` and
`webhook_deliveries`, additive, with the existing rows untouched. Migrations do
not run at boot here, which is worth remembering — the code deploying is not the
same as the schema being there.

## Phase 11 finished — applications

The last piece. A personal access token is a credential its owner pastes into
their own script; an application is how a program asks *another* person for
access to their drives, without that person ever handing over a password.

A small subset of OAuth 2.1, and the omissions are the point: only the
authorisation code flow, PKCE always rather than optionally, exact redirect
matching rather than prefix, codes hashed, usable once, and for a minute. The
implicit flow and the password grant are absent — both hand a credential to
somewhere it cannot be kept, and both were removed from the specification for
that reason.

Every check in the exchange is one that has been the subject of a real attack. A
code redeemed twice revokes the grant the first redemption created, because a
second attempt means somebody else has the code. Refresh tokens rotate on every
use. An unregistered redirect is an error page and **never** a redirect — sending
the error to the address in the request is how an open redirect gets built out
of an authorisation server. An application cannot be granted more than it
registered for, whatever the URL asks for.

`/oauth/authorize` is not a page. It validates and hands the browser to Orbit's
own consent screen, so the thing somebody reads before granting access to their
drives is rendered by the app they already trust and are already signed in to —
and every failure happens before anything with an Allow button on it is drawn.

Access tokens are resolved by the same call path as personal tokens, so every
`/v1` route treats the two identically. A route that had to ask which kind it
was looking at would eventually be a route that forgot to.

## The .vercel.app address

Reported as not working: the Vercel-generated URL loads and then says "Could not
reach Orbit". It is refused by CORS — the API allows one origin, the real one —
and that is the smaller half of the problem.

The larger half is the session cookie. It is set by `api.orbit.harshitsaini.in`
for `.harshitsaini.in` with `SameSite=Lax`, and a request from `*.vercel.app` is
cross-*site*, not merely cross-origin, so the cookie is not sent at all.
Supporting that address would mean `SameSite=None` — a third-party cookie, which
Chrome and Safari are in the middle of taking away. Sign-in would work for some
people and fail for others with no way to tell which.

So the address redirects to the real domain instead. The URL works, in the sense
that it takes somebody to Orbit, without a cookie arrangement that is being
deprecated underneath it.

**Production migrated** for the three OAuth tables, additive, existing rows
untouched.

## Phase 21 — sending a file straight to somebody

The last phase on the board. A file goes browser to browser over WebRTC: it does
not reach Orbit's server, is not put in a drive, and nothing is left when the
tabs close. Orbit's whole part is introducing the two ends over the WebSocket it
already has, and what it passes between them is opaque to it — a relay that
understands what it carries is a relay somebody is later tempted to log.

**It costs nothing and is built so that it cannot start costing.** WebRTC needs
two supporting services. STUN, which tells a browser what its address looks like
from outside, is free and account-free. TURN, which relays the bytes when two
networks have no direct path, is bandwidth somebody pays for — and it is the one
thing here that would become a bill.

So there is no TURN and there will not be. About one attempt in ten cannot
connect without it, and the answer is to notice, say so in plain words, and
point at the ordinary path: upload it and share a link, which Orbit already
does. A transfer that silently never starts is the failure worth avoiding.

The signalling is confined to channels beginning `p2p:`. Without that prefix
check, anything with a socket could publish a fake `upload:complete` to any
upload it could name — there is a test that tries exactly that. A handoff has
two ends and a third arrival is refused; the id is the capability, as with a
share link, and it lives in the URL **fragment**, which a browser never sends to
a server. It is therefore not in Orbit's logs, Vercel's, or any proxy between.

### Two bugs, and the test that caught the second

**The offer went out before there was anyone to offer it to.** The sending end
created its offer as soon as it was ready, the relay had nobody to pass it to,
and nothing stores it — so the receiver joined into silence and both sides sat
waiting, which looks exactly like two networks that cannot reach each other. The
offer now waits for the far end to arrive, and the connection timeout starts
then rather than at page load.

**A `subarray` is a window onto a larger buffer.** Sending `leftover.buffer` put
the *entire* source chunk on the wire instead of the few hundred bytes left over
from it, and the file arrived nearly twice as long as it was sent. The
end-to-end test downloads the file and compares it byte for byte, which is what
found it — a test that only checked the transfer finished would have passed.

The test runs two real browser contexts, a real WebRTC connection and a real
download, and asserts that no request carrying the file ever reached an upload
route. The case that fails in the wild — two networks with no path between them
— has no test, because it has no fix: bridging it needs a relay, a relay is a
bill, and the product's answer is to say so.

The privacy policy gained a section: a direct transfer contacts a public STUN
server, which sees an IP address and nothing else. Every claim on that page has
to stay true, and this was a new one.
