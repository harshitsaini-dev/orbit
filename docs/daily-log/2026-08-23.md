# 23 August 2026

## Google, published

The app is **In production**. Google accepted the homepage, `/privacy` and
`/terms` and published it without demanding verification — so the seven-day
refresh token expiry is gone, and any Google account can connect rather than
only the test-user list.

Two things carry forward: the app is published but unverified, so a new user
sees "Google hasn't verified this app" and has to choose Advanced → Continue;
and an unverified app on a restricted scope has a 100-user lifetime cap that
cannot be reset. Full verification of the `drive` scope means an annual
third-party security assessment that is not free, so it waits until Orbit is
actually being opened to a crowd.

The console's **Data access** page lists no scopes at all, which is expected —
Orbit asks for them in the authorisation request rather than registering them
on the consent screen. It is probably also why publishing went through
unchallenged, and it is the reason to leave that table empty.

**One correction worth recording.** The advice written here first was to
disconnect the drive and reconnect it, to get a token issued outside Testing.
That is wrong: disconnecting cascades, taking the drive's share links, its
collection items, its transfer history and any grants given to other people
with it. Connecting an account Orbit already has updates that row in place, so
a reconnect costs nothing. The docs say so now.

## Dropbox, nothing to do

The 50-account cap written in these docs was wrong. Development status links up
to **500** users, and Dropbox's own production request form says that an app
which does not need more than 50 should not apply, and that an application is
not reviewed until the app already has 50 users.

Branding is filled in anyway — that is what the authorise screen shows, and a
puzzle-piece icon with no publisher reads as something not to grant access to.
Icons at 64 and 256 were generated for it. Revisit at 50 accounts, when Dropbox
allows two weeks to apply.

## Privacy and terms

Written because Google needed them, kept because an app that asks for somebody's
whole Drive owes them a plain account of what it does with it. Both public,
outside the auth gate — a consent screen links to the policy for somebody who
has not signed in and may be deciding not to.

Every claim maps to something in the source: AES-256-GCM for provider tokens, a
SHA-256 hash for API tokens, no file bytes on disk at any point, no provider URL
reaching the browser, a device class and no IP for a public link, ninety days of
retention. The Limited Use paragraph is there because it is accurate, not as a
formality.

## Downloads: four asked for, one arriving — then none

Two goes at this one.

The content URL is on the API's own origin, and a link's `download` attribute is
ignored cross-origin — so every hidden anchor was a top-level navigation, and
starting the second aborted the first before the provider had answered.

Hidden frames fixed the cancellation and broke everything else: they depend on
the API's framing headers being exactly right, which is a lot of distance
between pressing Download and a file appearing.

The answer was to stop needing anything from the server. Each file is fetched
and handed over as a blob; a blob URL is same-origin, so `download` means
something again — real filenames, no navigation, nothing to cancel. One at a
time, each released as soon as it is taken, so only one file is held at once.
The API went back to refusing every frame.

## Dragging inside the grid offered to upload what was already there

Chrome puts `Files` in the transfer when an `<img>` is dragged, so nudging a
thumbnail across the grid raised the upload overlay — and letting go uploaded a
second copy of the file that thumbnail was of. A drag that began inside the page
is ignored now, and thumbnails are not draggable at all.

## A phone has no right button

Every action except delete lived behind the context menu, so on a touch screen
copy, move, share and the rest were simply unreachable. The selection bar has an
Actions button now, opening the same menu — one list of actions rather than a
second one that drifts.

And the page says which drive it is showing. The switcher only appeared with two
accounts connected, so with one there was nothing naming the provider or the
account; on a phone, with no sidebar either, nothing at all.

## Duplicates, on a screen it fits on

The header pushed two of three things right with `margin-left: auto`, which
wrapped into three ragged right-aligned rows with no common edge to read down,
and left the set's two actions half off the screen.

The rows had it backwards as well. Every copy in a set has the same name — that
is what makes it a set — so the name is the one thing identifying nothing, and
the path is the only thing that tells two copies apart. The name had the room
and the path was cut, and which drive a copy was on, the whole question when the
copies are on two different clouds, was hidden outright below 700px.

A real bug fell out of it. The path was shortened with `direction: rtl` and an
ellipsis, which renders a leading slash at the right-hand end — `/a/b/photo.jpg`
was drawn as `…b/photo.jpg/`, a path that does not exist. It is shortened in
code now. Bidirectional text reordering is not a truncation tool.

## Phase 20 — reading the text in a picture

Both halves, and the phase is done.

The server stores readings and searches them. A reading under 45 confidence or
8 characters is refused rather than kept: an unreadable photo produces
confident-looking noise, and the costs are not symmetric — a missing result is a
search that fails visibly, a wrong one is a search that lies. Refusing also
clears any earlier reading, because the reading is about the file and the file
has changed. `LIKE` rather than FTS5; this holds one person's receipts, and a
virtual table with triggers to keep it in step is a cost to pay when the
difference can be felt.

The client is Tesseract compiled to WebAssembly, in a Web Worker. Nothing is
uploaded — the bytes the browser already fetched to draw the picture are the
bytes it reads, and only the resulting string comes back. That is the whole
economics of the feature: server OCR is a bill per page, and a product whose
first rule is that it stores none of your files has no business posting them to
a vision API instead.

The engine is served from Orbit's own origin. The CSP allows scripts and workers
from `'self'` only, and loading a CDN worker would tell a third party who is
scanning what — which the privacy policy says does not happen.
`scripts/vendor-tesseract.mjs` copies three LSTM core builds out of node_modules
and downloads the fast trained data at build time: 14 MB, gitignored, and
excluded from the service worker so no install of Orbit pays for a feature most
sessions never touch. A browser fetches about six megabytes of it, once.
`'wasm-unsafe-eval'` had to go into the CSP — it permits WebAssembly and nothing
else.

Scanning is asked for and never automatic. It says what it will cost before it
starts, it can be stopped in the middle, and everything read up to that point is
kept. Files already read are skipped, so scanning a folder, adding two photos
and scanning again costs two.

Results found this way carry the line they matched on, because a file called
`1759653621497799480627.jpg` appearing in the results for "sharbat" reads as a
bug until the reason is beside it.

**A bug worth remembering.** The first run finished instantly having read
nothing. The cancel flag is a ref, set to `true` in an effect cleanup — and
StrictMode mounts, unmounts and mounts again in development, so that cleanup ran
once before anybody had pressed anything. A flag only ever set to `true` meant
the loop stopped on its first check, every time, in a way that looked exactly
like OCR finding nothing at all. It is cleared on the way in now as well as set
on the way out.

The end-to-end test runs the real engine over a rendered receipt and asserts the
words that come back — `NATIONAL MARKET`, `17842`, confidence above 60. A mocked
engine would only prove that a button calls a function.
